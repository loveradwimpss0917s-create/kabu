### 1-1. EMA判定条件の相違 — ✅ 妥当（指摘より深刻）

**worker.js:242-245**（スキャナーが使う）
```js
if (cur > e20 && e20 > e50 && e50 > e200) { score += 15; emaSignal = 'perfect-up'; }
else if (cur < e20 && e20 < e50 && e50 < e200) { score -= 10; emaSignal = 'perfect-down'; }
else if (cur > e20 && e20 > e50)             { score += 8;  emaSignal = 'partial-up'; }
else if (cur > e20)                          { score += 5;  emaSignal = 'above-ema20'; }
```

**index.html:925-943**（詳細画面が使う）
```js
if(e20&&e50&&e200&&e20>e50&&e50>e200){ add('EMA配列',+15,...) }
else if(e20&&e50&&e200&&e20<e50&&e50<e200){ add('EMA配列',-10,...) }
else if(e20&&e50&&e20>e50){ add('EMA配列',+8,...) }
else if(e20&&e50&&e20<e50){ add('EMA配列',-5,...) }   // ← workerには存在しない分岐
else { add('EMA配列',0,'EMA配列 データ不足',...) }      // ← workerには存在しない分岐
```

確定した差異:
- worker は全分岐で **`cur`（現在値）とEMA20の位置関係を必須条件**にしているが、index.html は `cur` を一切参照しない。
- 第4分岐が**正反対**: worker は `cur > e20` で **+5点**、index.html は `e20 < e50` で **−5点**。
- 同一入力で最大 **10点差**（+5 vs −5）が発生しうる。10点はシグナル境界（75/90）を跨ぐに十分。

**指摘より深刻な点（評価者は未言及）**: 差異はEMA判定条件だけではなく、**指標計算関数そのものが別実装**である。

| 関数 | worker.js | index.html | 影響 |
|---|---|---|---|
| `calcEMA` | `closes[0]` をシード、全indexに値 | 先頭p本のSMAをシード、p-1까지null。加えて `if(!v){return null}` により値が falsy の足で null を返す | EMA系列が根本的に別物 |
| `calcATR` | Wilder平滑・**配列**を返す | 直近p本の**単純平均・スカラー**を返す | ATR%が別値 |
| `calcRSI` | null埋め位置が異なる | `while(r.length<p)r.unshift(null)` | 参照indexがずれうる |
| `calcMACD` | 全系列にEMA | null除去→EMA→再マッピング | hist系列が別物 |

→ 「同一銘柄でスコアが食い違う」は事実であり、原因は条件分岐の差だけでなく**スコアエンジン全体が二系統ある**こと。

### 1-2. `adjclose` 未使用 — ✅ 妥当（影響の説明は ⚠️ 訂正が必要）

指定されたコマンドの**生出力**:
```
$ grep -n "adjclose" worker.js index.html
(ヒット0件・終了コード1)

$ grep -n "includeAdjustedClose" worker.js index.html
worker.js:337:  const params = new URLSearchParams({ interval: '1d', range: '1y', includeAdjustedClose: 'true' });
```

事実: `includeAdjustedClose=true` は worker.js の**スキャナー経路のみ**が要求し、`adjclose` フィールドは**リポジトリ全体で一度も読まれていない**。index.html は要求すらしていない（`fetchYahooChart` のURLに当該パラメータなし）。

**⚠️ 評価者の説明を訂正する**: 評価者は「**分割**銘柄で全テクニカル指標が歪む」と述べたが、これは不正確である。Yahoo Finance の `v8/finance/chart` が返す `quote[].close` は**株式分割については調整済み**であり、`adjclose` が追加で調整するのは主に**配当**である。したがって実害は「分割で指標崩壊」ではなく「**配当落ち分（日本株大型で年2%前後、権利落ち日に0.5〜1%の段差）がリターンと指標に混入する**」というより軽度なものである。

ただし**バックテストにおいては軽度では済まない**: 3年間で配当を無視すると累積リターンが系統的に過小評価され、「スコアの優位性」の測定値そのものが歪む。よって修正は必要（優先度は後述の通りバックテスト前）。

### 1-3. 決算スコアの矛盾 — ⚠️ 部分的に妥当

両ブロックの正確な関係:

- **index.html:989**（`calcTradeScore` 内 = **スコアに加算**）
  `daysEar>=0 && daysEar<=7` → `add('材料', +15, ...)`
- **index.html:1375**（`analyze()` 内 = **スコア確定後、ラベルのみ上書き**）
  `daysToEarnings>=0 && daysToEarnings<=3` → `signalClass='neutral'` / `ts.signal='NEUTRAL'` / `vClass='hold'`

**判定の根拠**: 除外処理は `score` 変数を**一切変更していない**。変更しているのは表示ラベルだけ。したがって:

| 決算までの日数 | スコアへの+15 | ラベル保護 | 実際の挙動 |
|---|---|---|---|
| 0〜3日 | **適用される** | あり（NEUTRAL強制） | リングゲージ・`psbarScore` は**+15された数値のまま**表示され、ラベルだけ中立。数値とラベルが不一致 |
| **4〜7日** | **適用される** | **なし** | **決算が近いことを理由にスコアが上がり、BUY/STRONG BUYが出る。無防備** |

→ 評価者の「矛盾」という表現は**同一レイヤでの相殺**を示唆するが、実際は「**スコア層とラベル層の不整合**」であり、かつ**真に危険なのは評価者が言及していない4〜7日の窓**である。この窓では、決算という結果が二値的に振れるイベントの直前であることが「カタリスト大！」として**買い材料に計上される**。

**定量的な妥当性評価（設計判断の根拠）**: 決算前後の超過リターン（earnings announcement premium）は学術的には実在が報告されている（Beaver 1968, Frazzini & Lamont 2007 等）。したがって符号（プラス）は文献上まったくの出鱈目ではない。**しかし規模が破綻している**: 報告されている premium は1決算あたり0.2〜0.3%程度である一方、本アプリの +15点 は0〜100スケールで**出来高の+20に次ぐ第2位の加点**であり、シグナル境界を単独で跨げる大きさである。同時に決算跨ぎはボラティリティが数倍に拡大する。**レバレッジ運用を目的とする本アプリにおいて、0.3%の期待値のために分散を数倍にする取引を第2位の重みで推奨する設計は、リスク調整後で明確に不合理**である。

→ 結論: 「矛盾」ではなく「**レイヤ不整合＋無防備な4〜7日窓＋期待値に対して10〜50倍過大な重み**」。修正対象として妥当。

### 1-4. cronが構造的に毎回失敗 — ✅ 妥当（原因確定）

評価者は「複合原因の可能性」を提示したが、**単一原因に特定できた**。

**根拠1: 実行プランの確定** — 開発者自身のコミット `c570a44` の本文:
```
fix: on-demand scan上限を45銘柄に制限 — Cloudflare Workers 50 subrequest制限対策

手動スキャン時は45銘柄(+crumb/Supabase計4リクエスト=49)に制限し上限以内に収める。
cronジョブは引き続き全81銘柄をスキャン。
```
→ 50サブリクエスト上限（**無料プラン**）であること、**cron経路を意図的に未修正で残したこと**が開発者自身によって文書化されている。

**根拠2: cron経路のサブリクエスト実数**
- `scheduled()` (worker.js:586) は `runScanner(env)` を **maxStocks 未指定**で呼ぶ
- `runScanner` (worker.js:399): `maxStocks ? SCAN_STOCKS.slice(0, maxStocks) : SCAN_STOCKS` → **全81銘柄**（実測81件）

| 処理 | fetch数 |
|---|---|
| `getCrumb()`（fc.yahoo.com + getcrumb） | 2 |
| `getMarketCondition()` | 1 |
| `scanStock` × 81 | 81 |
| Supabase DELETE | 1 |
| Supabase INSERT | 1 |
| **合計** | **86**（上限50） |

**失敗の連鎖（コード上で確定）**:
1. 51件目以降の `fetch` が "Too many subrequests" で throw
2. 48銘柄目以降の `scanStock` は自身の `try/catch`（worker.js:385）で握り潰され `null` を返す → **エラーが表面化しない**
3. worker.js:442 の **Supabase DELETE は try/catch で保護されていない** → throw が `runScanner` を貫通
4. `scheduled()` の `.catch()` が `Cron scanner失敗` をログ出力して終了 → **Supabaseへの書き込みは一切行われない**

**他候補の否定**:
- **24秒タイムアウト（`MAX_SCAN_MS`）は原因ではない**。サブリクエスト上限に達した後の `fetch` は待たずに即失敗するため、後続バッチは瞬時に終わる。ループが24秒に達する前に完了する。
- **crumb取得失敗も原因ではない**。crumb は最初の2サブリクエストで取得され、上限に達する前に成功する。

**副次的発見（データ消失の潜在リスク）**: 手動経路（44銘柄）の内訳は 2+1+44+DELETE(48)+INSERT(49) = **49** で上限まで残り1。crumbの再取得が1回発生する、または `SCAN_STOCKS` が2件増えるだけで、**DELETE が成功し INSERT が失敗する**状態に入る。その場合「当日データを削除したまま復旧しない」。現状は**偶然1リクエストの余裕で回避されているだけ**であり、upsert化（後述 Task C）は必須。

### 1-5. `/api/scan-trigger` 無認証・CORS — ✅ 妥当（重大穴を追加発見）

- **認証**: `handleScanTrigger`（worker.js:513-530）は `OPTIONS` 判定 → メソッド判定 → 即 `runScanner(env, 44)`。**トークン・Origin・レート制限の検証は一行も存在しない**。
- **CORS**: `corsHeaders()`（worker.js:543-549）が `Access-Control-Allow-Origin: '*'` を返し、これが scan-trigger を含む全ハンドラに適用されている。

**評価者が未言及の、より重大な穴 — `/yfin/*` がオープンプロキシ**:
```js
// worker.js:82
const path = url.pathname.replace(/^\/yfin/, '');
const targetUrl = `${YF_BASE}${path}?${params.toString()}`;
```
パスの許可リストが**存在しない**。任意の第三者が本デプロイを経由して Yahoo Finance の任意エンドポイントを、**Yahooのcrumb認証付きで**叩ける。濫用されればYahoo側でレート制限・IPブロックを受け、**アプリ本体が機能停止する**。scan-trigger の無認証（自分の無料枠を焼かれる）より、こちらの方が可用性への影響が大きい。

**脅威モデルの正直な整理**（過大評価を避けるため）: 本アプリは認証機能もセッションもなく、扱うデータは公開株価とローカルの取引記録のみ。したがって**情報漏洩リスクは低い**。実害は (a) 無料枠・Yahoo接続性の枯渇による**可用性喪失**、(b) `scan_results` の改竄、(c) XSS（`renderNews` の無エスケープ挿入、index.html:1711-1716。`href` にスキーム検証がないため `javascript:` も通る）による**localStorage内の取引記録の窃取・破壊**。優先度は「情報漏洩」ではなく「可用性とデータ完全性」で判断すべき。

## 2. 実装順序（Task 4）

**順序には技術的依存があり、入れ替えてはならない。** 各段階の「なぜ先か」は必ず読むこと。

```
Phase A（独立・即時）      A-1 scan-trigger認証  /  A-2 yfin許可リスト  /  A-3 XSS
        ↓（依存なし。ただし現在公開中の穴を塞ぐため先行）
Phase B（データ完全性）    B-1 upsert化 ──→ B-2 cron分割
        ↓（B-1なしにB-2をやると2回のcronが互いのデータをDELETEする）
Phase C（測定の前提）      C-1 指標一本化 ──→ C-2 調整後株価
        ↓（C完了前にバックテストしても「アプリが表示する数値」を測ったことにならない）
Phase D（中核仮説の検証）  D-1 バックテスト実行 → D-2 判定
        ↓（Dの結果なしにEを決めるのは、また根拠のない重みを作るだけ）
Phase E（結果に基づく改修） E-1 決算ロジック  /  E-2 加点重みの再設計
```

### 順序制約の理由（実装者は必ず理解すること）

1. **C-1（指標一本化）は D（バックテスト）の絶対的な前提**
   バックテストは「このアプリが表示するスコア」の優位性を測るものである。現状スコアエンジンは二系統あり、どちらを測っても**もう一方の画面が表示する数値については何も言えない**。二系統ある限りバックテスト結果は解釈不能。**これが本プロジェクト最大の順序制約。**

2. **C-2（調整後株価）は D の前**
   バックテストのリターン計算と指標の入力系列は同一の調整済み系列でなければならない。D の後に C-2 を入れると、バックテスト結果は破棄してやり直しになる。

3. **B-1（upsert）は B-2（cron分割）の前**
   B-2 は1日に2回 cron を走らせる設計。現行の DELETE→INSERT のままでは、**2回目の実行が1回目の保存分をDELETEする**（`scan_date=eq.${today}` で日付単位削除のため）。B-1 を先に入れること。

4. **E（決算ロジック・重み再設計）は D の後**
   現状の重み（出来高+20、EMA+15、決算+15…）はいずれも統計的裏付けなく設定されている。ここで「勘で直した新しい重み」に置き換えても、根拠のない数字が別の根拠のない数字に変わるだけである。**D で各項目の実測相関を得てから決める。**
   ただし例外として、決算+15 の**削除**だけは D の結果を待たずに実施してよい（理由は §3 Task E-1 に記載）。

5. **Phase A は依存なし**。ただし現在アプリは公開状態にあり、穴は今この瞬間も開いている。工数も小さいため最初に置く。

## 3. 各タスクの詳細仕様

### Task A-1: `/api/scan-trigger` の認証

- **対象ファイル**: `worker.js`（`handleScanTrigger`, `corsHeaders`）, `index.html`（`triggerScan`）, `README.md`
- **変更前の状態**: 認証チェックなし。誰でも `curl -X POST https://<host>/api/scan-trigger` でスキャンを起動でき、CORS は `*`。
- **変更後の期待動作**:
  - `X-Admin-Token` ヘッダが `env.ADMIN_TOKEN` と一致する場合のみ実行。不一致・欠落は **401**。
  - `env.ADMIN_TOKEN` が未設定の場合も **401**（フェイルクローズ。未設定で全通しにしないこと）。
  - このエンドポイントのレスポンスに **CORSヘッダを付与しない**（同一オリジンからのfetchのみ成立させる）。

- **トークンのライフサイクル設計**（iPad運用・CLIなしを前提とすること）:

  | 段階 | 方法 | 注意 |
  |---|---|---|
  | 生成 | パスワードマネージャ（iCloudキーチェーン/1Password）の生成機能で **32文字以上のランダム文字列** | **`openssl rand` や `wrangler secret put` を手順書に書かないこと**。CLIが無い環境である |
  | 保管（サーバ） | **Cloudflareダッシュボード** → Workers & Pages → 該当Worker → Settings → Variables and Secrets → **Encrypt** を選択して追加 | `wrangler.toml` の `[vars]` に**書かない**（平文でGitに載る） |
  | 保管（クライアント） | 初回操作時に `prompt()` で入力させ `localStorage` に保存 | **HTML/JSソースにトークンを埋め込まないこと** |
  | 検証 | 下記シグネチャ参照 | 401受信時はクライアント側で `localStorage` から削除し再入力を促す |

- **インターフェース仕様**:
  ```
  timingSafeEqual(a: string, b: string) => Promise<boolean>
    実装方針: 両者を SHA-256 でハッシュ化し、固定長バイト列を全バイト XOR 累積で比較する。
              文字列長・先頭一致長からのタイミングリークを避けるため、途中 return しないこと。
              （Cloudflare独自の crypto.subtle.timingSafeEqual を使う場合も、
                長さの異なる入力で例外を投げる点に注意し、必ずハッシュ後に比較すること）
  ```

- **影響範囲**: `index.html` の `triggerScan()` がヘッダ付与と401ハンドリングを行う必要がある。Task D 以降でバックテスト起動APIを作る場合も同じトークンを再利用する（新規トークンを増やさない）。

- **完了判定基準**:
  1. `X-Admin-Token` なしのPOSTが **401** を返す
  2. 誤ったトークンのPOSTが **401** を返す
  3. 正しいトークンのPOSTが **200** と `{ok:true, scanned:N}` を返す
  4. `wrangler.toml` を全文検索してトークン値が存在しない
  5. ブラウザで `view-source:` してトークン値が存在しない

- **注意点**: `env.ADMIN_TOKEN` 未設定時に「認証をスキップして通す」実装にしないこと（設定漏れが無防備状態に直結する）。

### Task A-3: `renderNews` のXSS

#### D-1-1. 実行環境の決定 — **GitHub Actions 上の Node.js スクリプト**

指示された2案はいずれも単独では成立しない。判断根拠を示す:

| 案 | 判定 | 理由 |
|---|---|---|
| Cloudflare Worker 上で実行 | ❌ 不採用 | **無料プランのCPU時間上限は1実行あたり10ms**。実測で1銘柄756営業日分のスコア再計算に約170msのCPUを要する（`slice` によるO(n²)コストを含む）。上限内に収めるには1実行あたり約40営業日が限界で、81銘柄×756日には**約1,530回の実行**が必要。毎分cronでも25時間以上かかり、途中で1回でもCPU超過すれば停止する。研究用途に耐えない |
| ローカル Node.js スクリプト | ❌ 実行不能 | 利用者はiPad運用でCLIを持たない（本書の制約条件） |
| **GitHub Actions 上の Node.js スクリプト** | ✅ **採用** | 実体は「Node.jsスクリプト」であり、実行場所がGitHubのランナーになるだけ。CPU上限なし（1ジョブ6時間）、サブリクエスト上限なし。**`workflow_dispatch` によりGitHubのWeb UIから起動でき、iPadのブラウザで完結する**。結果JSONをリポジトリにコミットして返せば、これもiPadのブラウザで閲覧できる |

**データ取得量の確認**: 81銘柄 × `range=5y&interval=1d` = **81リクエストのみ**（1銘柄1リクエストで5年分が返る）。レート制限対策はリクエスト間に1〜2秒のスリープを入れれば十分で、バッチ分割の必要はない。総データ量は約25MB程度。

#### D-1-2. ルックアヘッドバイアスを混入させない実行構造

**設計原則: 「未来を参照しない」ではなく「未来を参照できない」構造にする。**
インデックス `i` を渡して関数内部で `arr[i+1]` を読めてしまう構造ではなく、**`arr.slice(0, i+1)` で切り出した配列そのものを渡す**。こうすればスコア関数は未来のデータを物理的に保持していないため、実装ミスによる混入が**原理的に不可能**になる。

```
FOR EACH stock IN SCAN_STOCKS:
    series ← fetch(stock, range=5y, interval=1d)
    (O, H, L, C, V, dates) ← applyAdjustment(series)   # Task C-2 と同一の比率方式

    WARMUP_END ← 250          # EMA200 が意味を持つまで捨てる
    MAX_HORIZON ← 20
    EVAL_END ← length(C) - 1 - MAX_HORIZON

    FOR i FROM WARMUP_END TO EVAL_END:
        # ── ここから先、参照してよいのは添字 0..i のみ ──
        score ← calcTradeScore(
                    O.slice(0, i+1), H.slice(0, i+1), L.slice(0, i+1),
                    C.slice(0, i+1), V.slice(0, i+1),
                    summaryData = null,        # 理由は D-1-6
                    interval = '1d'
                )

        # ── ここから先は将来データ。エントリーは必ず翌営業日の「始値」 ──
        entry ← O[i+1]
        IF entry is invalid THEN continue
        ret_1  ← (C[i+1]  - entry) / entry
        ret_5  ← (C[i+5]  - entry) / entry
        ret_20 ← (C[i+20] - entry) / entry

        emit_row(stock, dates[i], score, score.details, entry, ret_1, ret_5, ret_20)
```

**実装者が守るべき4点**:
1. **エントリーは `C[i]`（当日終値）ではなく `O[i+1]`（翌営業日始値）**。スコアは当日の終値が確定して初めて計算できるため、その時点で約定可能な最初の価格は翌日の寄付である。当日終値でエントリーしたことにすると、実行不可能な取引を前提とした過大評価になる。
2. **`slice` を使うこと**。インデックス渡しにしないこと。
3. **`WARMUP_END` を250以上にすること**。EMA200はシード直後は収束しておらず、warmupが短いと初期の数十日のスコアが系統的に歪む。
4. **調整系列は D と C-2 で同一の関数を使うこと**。別実装にすると、アプリが見ている価格とバックテストが見ている価格が食い違う。

#### D-1-3. ベンチマークと集計方式

**分母・分子の定義（最重要）**: 「平均リターンがプラスだった」では**何も検証したことにならない**。対象期間に日本株全体が上昇していれば、ランダムなシグナルでもプラスになる。したがって**主指標は市場に対する超過リターンとする。**

```
benchmark_ret(date, h) ← 同一日・同一ホライズンにおける、
                          バックテスト対象81銘柄すべての ret_h の単純平均

excess_ret(row, h)     ← row.ret_h - benchmark_ret(row.date, h)
```

**なぜ日経225ではなく「対象ユニバースの等加重平均」を使うか**: 検証したいのは「スコアが**銘柄を選別**できるか」であり、「日本株を持つべきか」ではない。同じ81銘柄の中での相対比較にすることで、市場全体の変動・セクター偏り・対象期間の地合いをすべて相殺できる。日経225との比較は参考値として併記してよいが、判定には超過リターンを使うこと。

**スコア帯（バケット）**: アプリが実際に表示するシグナル境界と一致させること。これにより結果が「BUYと表示された銘柄は本当にNEUTRALより上がったのか」という問いに直接答える形になる。

| バケット | スコア範囲 | アプリ上の表示 |
|---|---|---|
| B1 | 0〜30 | STRONG SELL |
| B2 | 30〜50 | SELL |
| B3 | 50〜75 | NEUTRAL |
| B4 | 75〜90 | BUY |
| B5 | 90〜100 | STRONG BUY |

各バケット × 各ホライズン（1/5/20日）について算出する項目:
`n`, `平均超過リターン`, `中央値超過リターン`, `標準偏差`, `勝率(超過>0の割合)`, `平均生リターン`, `平均ベンチマークリターン`

#### D-1-4. 統計的有意性の判定

**素朴なt検定を使ってはならない。** 本データは2重に独立性を欠く:
- **時系列の重複**: 20日リターンを毎日計算すると、連続する行は19日分のデータを共有する
- **横断面の相関**: 同じ日の81銘柄は市場要因で強く相関する（超過リターン化で大幅に緩和されるが完全には消えない）

**採用する手法: 日付クラスタ・ブートストラップ**
```
REPEAT 2000 times:
    resampled_dates ← 全営業日から復元抽出（元の日数と同数）
    その日付に属する行を全て集める（同一日の銘柄はまとめて選ばれる = クラスタ）
    各バケットの平均超過リターンを再計算 → 分布に記録
95%信頼区間 ← 分布の 2.5 パーセンタイルと 97.5 パーセンタイル
```
日付単位でリサンプリングすることで、横断面相関と時系列重複の両方を扱える。実装は単純なループで済み、外部統計ライブラリを必要としない。

**補助的な頑健性チェック（両方必須）**:
- **単調性**: B1→B5 の平均超過リターンが単調増加しているか。バケット順位と平均超過リターンの **Spearman順位相関 ρ** を算出する。単一バケットのp値より、この単調性の方がはるかに強い証拠となる。
- **サブ期間安定性**: 3年間を1年ずつ3分割し、各期間でB4+B5の超過リターンの符号を確認する。

#### D-1-5. 採用基準（**実行前に固定すること**）

結果を見てから基準を決めると、必ず「優位性あり」という結論が作れてしまう。以下を**実装開始前に確定**させ、変更しないこと。

> **「スコアに優位性あり」と判定する条件（3つすべてを満たすこと）**
> 1. B4+B5（スコア75以上）の **20日超過リターン（摩擦控除後）** について、ブートストラップ95%信頼区間の**下限が0を上回る**
> 2. 5バケットの平均超過リターンの **Spearman ρ ≥ 0.8**（概ね単調増加している）
> 3. 3つの1年サブ期間のうち **2つ以上**でB4+B5の超過リターンが正
>
> **1つでも欠けた場合の結論は「優位性を確認できなかった」であり、これを正しい成果として報告すること。**

**生存者バイアスに関する必須の補正解釈**: `SCAN_STOCKS` は**現在の**大型株81銘柄のハードコードされたリストである。3年前に遡って検証する以上、「3年間生き残り、今も大型株である銘柄」だけを対象にしていることになり、**結果は構造的に上方バイアスを持つ**。これを完全に除くには、各時点の時価総額上位を再現する point-in-time ユニバースが必要であり、Yahoo Financeからは取得できない（対応は本タスクのスコープ外とする）。

したがって実装者は:
- レポートに**バイアスの存在と方向（結果を良く見せる方向）を必ず明記**すること
- 上記基準を辛うじて満たす程度の弱い結果（例: 20日超過リターンが+0.1%程度）は、**「優位性なし」と解釈するのが妥当**である旨をレポートの結論欄に記載すること

#### D-1-6. 検証できない項目の明示

**項目⑧（材料・アナリスト）はバックテスト不能である。** 理由:
- Yahoo の `quoteSummary.calendarEvents` が返すのは**次回の**決算日のみで、過去の決算日履歴は取得できない
- `financialData.recommendationKey` は**現在の**アナリスト評価であり、過去時点の評価ではない

過去のシミュレーションに**現在の**アナリスト評価を持ち込めば、それ自体が重大なルックアヘッドバイアスとなる。よって `calcTradeScore` の呼び出しでは `summaryData = null` を渡し、**項目①〜⑦のみを検証対象とする**。この事実はレポートに明記すること。

**この制約は Task E-1 の設計根拠でもある**: 検証できない項目が、検証済みの項目と同じ土俵でスコアを±15点も動かしている状態は容認できない。

#### D-1-7. コスト計算式とパラメータ配置

パラメータは**スクリプト冒頭の設定オブジェクトに集約**し、`workflow_dispatch` の入力からも上書きできるようにすること（コード内に数値を散在させない）。

```
CONFIG = {
  feeBpsOneWay:      5,       # 片道手数料 5bps = 0.05%
  slippageBpsOneWay: 10,      # 片道スリッページ 10bps = 0.10%
  taxRatePct:        20.315,  # 譲渡益税（利益が出た場合のみ）
  horizons:          [1, 5, 20],
  warmupBars:        250,
  bootstrapIters:    2000,
}

friction     = 2 * (feeBpsOneWay + slippageBpsOneWay) / 10000   # 往復
netReturn    = grossReturn - friction
afterTaxReturn = netReturn > 0 ? netReturn * (1 - taxRatePct/100) : netReturn
```

**税の扱いに関する重要な設計判断**: **判定（D-1-5の基準）には `netReturn`（摩擦控除後・税引前）の超過リターンを使うこと。** 税引後を判定に使ってはならない。理由は、比較対象であるベンチマーク（ユニバース平均を買い持ちする戦略）にも同じ税がかかるためで、戦略側にだけ課税して比較すると**優位性を不当に過小評価する**。税引後の数値は「実際に手元にいくら残るか」の現実感を示す参考値としてレポートに併記する。

### Task E-1: 決算ロジックの是正

- **前提**: 本タスクのうち**「+15/+5 の削除」は Task D の結果を待たずに実施してよい**。理由は D-1-6 の通り、この項目は**構造的に検証不能**だからである。検証できない項目が、検証済みの項目と同じスコアに±15点を加算している状態は、バックテストの結果が出た後も正当化できない。
- **対象ファイル**: `indicators.js`（Task C-1 完了後の `calcTradeScore`）, `index.html`（`analyze()` の除外処理と表示）
- **変更前の状態**: §1-3 の通り。4〜7日窓が無防備、0〜3日はスコアとラベルが不整合。
- **変更後の期待動作**:
  1. `calcTradeScore` から **`材料`（決算日数による加点）を削除**する。決算の接近はスコアを動かさない。
  2. 決算までの日数は **veto（拒否権）フラグ**として `calcTradeScore` の戻り値に含める（例: `earningsVeto: { active: boolean, days: number }`）。閾値は**0〜7日**とする（現行の3日ではなく、削除する加点の窓と同じ7日に揃える）。
  3. veto が立っている場合、**表示されるスコア数値そのものを中立表示にする**（リングゲージと `psbarScore` がBUY相当の数値のまま残らないようにする）。ラベルだけを書き換える現行方式は採らない。
  4. `アナリスト`（recommendationKey による ±8）についても、**過去検証が不可能**である点は決算と同じ。ただし現在時点の判断材料としては有用性が残るため、**スコアからは外し、詳細画面に情報として表示するのみ**とする。
- **影響範囲**: スコアの取りうる最大値が下がるため、シグナル境界（75/90）に到達する頻度が変わる。**Task D のバックテストは項目⑧を除いた①〜⑦で実施されるため、この変更によりアプリの挙動とバックテストの前提が一致する**（むしろ整合性が向上する）。
- **完了判定基準**:
  1. 決算5日前の銘柄で、決算を理由とした加点が `details[]` に含まれない
  2. 決算2日前の銘柄で、表示スコア・ラベル・リングゲージのすべてが中立を示す（数値だけ高いまま残らない）
  3. 決算7日前の銘柄で veto が有効になる

### Task E-2: 加点重みの再設計

- **前提**: **Task D-1 の `itemAnalysis` 出力が入力である。本タスクは D の完了前に着手してはならない。**
- **対象ファイル**: `indicators.js`
- **設計方針**（実装者は D の結果を見てから以下の判断を行う）:

  | `itemAnalysis` の結果 | 取るべき対応 |
  |---|---|
  | 差の95%信頼区間が0を跨がず、符号が加点方向と一致 | 重みを維持。差の大きさに比例した相対重みへ調整 |
  | 信頼区間が0を跨ぐ（有意でない） | **重みを0にする**（項目自体はUI表示として残してよい） |
  | 符号が加点方向と**逆** | 重みの符号を反転させるのではなく、**まず0にする**。反転は同じデータで見つけた逆張りを過学習する危険があるため、別途サブ期間で再現性を確認してから判断する |

- **注意点**: D の結果が「優位性を確認できなかった（EDGE_NOT_CONFIRMED）」であった場合、**本タスクは「重みの調整」ではなく「スコアを売買判断に使うことをやめる」という意思決定になる**。その場合の最小限の対応は、UIから断定的な売買表現（`STRONG BUY` / `🟢ロング推奨` 等）を除去し、**検証されていない参考指標であることを明示する表示に変更する**ことである。この可能性を事前に受け入れた上で D を実行すること。
